# Event Listeners and Near-Cache Bloom Filters
## Event Listeners

### How Hot Rod handles listeners

Hot Rod uses explicit `ADD_CLIENT_LISTENER` / `REMOVE_CLIENT_LISTENER` request/response
opcodes. Each listener has a 16-byte `listenerId` generated by the client, and events are
pushed from the server on the same TCP connection, multiplexed with regular responses.
The server-side implementation (`ClientListenerRegistry`) maintains a map of
`listenerId → BaseClientEventSender`, where the sender is annotated as a `@Listener(clustered = true)`
and receives `CacheEntryCreated`, `CacheEntryModified`, `CacheEntryRemoved`, and
`CacheEntryExpired` events from the embedded cache.

Key aspects of the Hot Rod listener model:

- **Event types**: created (key + version), modified (key + version), removed (key only),
  expired (key only). Custom converter output uses a single `customEvent` payload.
- **Listener interests**: a 4-bit bitmask (`0x01` created, `0x02` modified, `0x04` removed,
  `0x08` expired) — a `0x00` value means "all events".
- **Filter and converter factories**: server-side `CacheEventFilterFactory` and
  `CacheEventConverterFactory` instances registered by name. The client specifies factory
  names and binary parameters at listener registration time. A combined
  `CacheEventFilterConverterFactory` is also supported.
- **includeCurrentState**: when `true`, the server replays all existing cache entries as
  synthetic `CREATED` events before sending live events. The replay events carry the
  original `messageId` so the client can distinguish them from live events.
- **Bloom filter**: optional client-side bloom filter of interesting keys — the server
  skips events whose key doesn't pass the bloom filter.
- **Backpressure**: `BaseClientEventSender` uses a `ConcurrentLinkedQueue` with a max size
  of 100. When the queue is full, the cache operation that triggered the event blocks
  (via `CompletableFuture`) until events are drained to the channel.
- **Channel disconnect**: the channel's `closeFuture` automatically removes the listener
  and unblocks any pending events.
- **Counter listeners**: separate `ClientCounterManagerNotificationManager` manages
  per-counter listeners with the same `listenerId`-based model, pushing counter value
  change events on the same connection.

### gRPC design: server-streaming RPCs

gRPC has a natural primitive for push-based events: **server-streaming RPCs**. Each
listener becomes a long-lived server-streaming call. This eliminates the need for:

- Custom listener IDs — the HTTP/2 stream itself identifies the listener
- Custom event multiplexing — HTTP/2 stream multiplexing handles it
- Custom backpressure — HTTP/2 flow control provides it

#### Cache event streams

```protobuf
// ---------- Cache event listener ----------

message CacheListenRequest {
  string cache_name = 1;

  // Event interest bitmask (same values as Hot Rod):
  //   0x01 = created, 0x02 = modified, 0x04 = removed, 0x08 = expired
  //   0x00 = all events
  int32 listener_interests = 2;

  // If true, the server replays all existing entries as CREATED events
  // before switching to live events. Replay events have is_replay = true.
  bool include_current_state = 3;

  // Optional key filter — only receive events for keys matching this set.
  // Empty means all keys.
  repeated bytes key_filter = 4;

  // Optional server-side filter factory name and parameters.
  string filter_factory = 5;
  repeated bytes filter_params = 6;

  // Optional server-side converter factory name and parameters.
  // When set, the event value is the converter output rather than the
  // raw cache value.
  string converter_factory = 7;
  repeated bytes converter_params = 8;
}

message CacheEvent {
  CacheEventType type = 1;
  bytes key = 2;

  // Present for CREATED/MODIFIED events (unless converter is used).
  // Not present for REMOVED/EXPIRED.
  optional bytes value = 3;

  // Entry version, if available.
  int64 version = 4;

  // True if this event is part of an includeCurrentState replay.
  bool is_replay = 5;

  // True if this event was caused by a retried command (e.g. after
  // topology change). Clients can use this to deduplicate.
  bool is_retried = 6;

  // For converter events — the converter output replaces value.
  optional bytes custom_event_data = 7;
}

enum CacheEventType {
  CACHE_EVENT_CREATED = 0;
  CACHE_EVENT_MODIFIED = 1;
  CACHE_EVENT_REMOVED = 2;
  CACHE_EVENT_EXPIRED = 3;
}

service CacheListenerService {
  // Opens a long-lived event stream for a cache.
  // The client cancels the RPC (or half-closes) to remove the listener.
  rpc Listen(CacheListenRequest) returns (stream CacheEvent);
}
```

### Lifecycle and cancellation

| Concern                   | gRPC approach                                                                                                                                                                                                                |
|---------------------------|------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------|
| **Register listener**     | Client opens the server-streaming RPC (`Listen` or `ListenCounter`)                                                                                                                                                          |
| **Receive events**        | Server sends `CacheEvent` / `CounterEvent` messages on the stream                                                                                                                                                            |
| **Remove listener**       | Client cancels the RPC (sends `RST_STREAM`), or the server completes the stream                                                                                                                                              |
| **Connection disconnect** | HTTP/2 connection close implicitly cancels all open streams → all listeners removed                                                                                                                                          |
| **Backpressure**          | HTTP/2 flow control: when the client stops reading, the server's `ChannelHandlerContext.write()` becomes non-writable, and the event sender can apply the same queue-and-block strategy as Hot Rod's `BaseClientEventSender` |

### includeCurrentState semantics

When `include_current_state = true`:

1. The server registers the embedded cache listener with `includeCurrentState = true`
2. Existing entries are replayed as `CacheEvent` messages with `type = CACHE_EVENT_CREATED`
   and `is_replay = true`
3. After all existing entries are replayed, live events follow with `is_replay = false`
4. The client can distinguish replay from live events using the `is_replay` field — simpler
   than Hot Rod's `messageId`-based approach

### Filter and converter factories

gRPC reuses the same server-side `CacheEventFilterFactory` / `CacheEventConverterFactory`
infrastructure as Hot Rod. The `filter_factory`, `filter_params`, `converter_factory`, and
`converter_params` fields in `CacheListenRequest` map directly to the factories registered
via `ClientListenerRegistry`.

Additionally, the `key_filter` field provides a simple client-specified key set filter
without requiring a deployed factory — covering the common case of "watch these specific
keys" without server-side code.

### Differences from Hot Rod

| Aspect                 | Hot Rod                                                      | gRPC                                                                                               |
|------------------------|--------------------------------------------------------------|----------------------------------------------------------------------------------------------------|
| **Listener identity**  | 16-byte `listenerId`                                         | HTTP/2 stream ID (implicit)                                                                        |
| **Event multiplexing** | Custom: events interleaved with responses on same connection | HTTP/2 stream multiplexing (each listener is its own stream)                                       |
| **Backpressure**       | Custom queue (max 100) + `CompletableFuture` blocking        | HTTP/2 flow control + optional application-level queue                                             |
| **Bloom filter**       | Client sends bloom filter of interesting keys                | `key_filter` field (explicit key set) — bloom filter optimisation possible as a future enhancement |
| **Cancellation**       | Explicit `REMOVE_CLIENT_LISTENER` request                    | `RST_STREAM` (RPC cancellation)                                                                    |
| **Disconnect cleanup** | `Channel.closeFuture()` callback                             | Same — HTTP/2 connection close cancels all streams                                                 |
| **Replay marker**      | `messageId` on replay events vs `0` on live                  | `is_replay` boolean field                                                                          |
| **Multiple listeners** | Multiple `listenerId`s on same connection                    | Multiple independent streams on same connection                                                    |

### Server-side implementation sketch

The gRPC event listener handler wraps the same embedded listener mechanism:

1. Parse `CacheListenRequest` to extract filter/converter factory names and params
2. Create a `@Listener(clustered = true)` annotated object that writes `CacheEvent`
   messages to the gRPC response stream (via `StreamObserver.onNext()` or the equivalent
   Netty-native write path)
3. Register the listener with the cache via `cache.addFilteredListenerAsync()`
4. When the stream is cancelled (client-initiated or connection close), remove the
   listener via `cache.removeListenerAsync()`

The key difference from Hot Rod's `BaseClientEventSender` is that there is no need to
manage a `listenerId → sender` map or multiplex events onto a shared channel. Each gRPC
stream is independent, and the Netty HTTP/2 stream channel provides natural isolation.

## Near-Caching with Bloom Filters

### Goal

Allow gRPC clients to implement a local near cache with bloom-filter-based invalidation,
matching the semantics of Hot Rod's `InvalidatedNearRemoteCache`. The server only sends
invalidation events for keys that the client's near cache *might* contain, avoiding
unnecessary network traffic.

### How Hot Rod implements it

The mechanism has three collaborating parts:

1. **Client-side near cache** (`NearCacheService`, `InvalidatedNearRemoteCache`):
   - Maintains a bounded local cache of recently-accessed entries.
   - On registration, sends a bloom filter bit count (`maxEntries × 4` bits by default)
     to the server via `ADD_BLOOM_FILTER_NEAR_CACHE_LISTENER_REQUEST`.
   - Tracks false positives (invalidation events for keys not in the near cache). When
     false positives exceed a threshold (`maxEntries / 16 + 3`), the client recalculates
     the bloom filter from current near cache contents and sends an
     `UPDATE_BLOOM_FILTER_REQUEST`.
   - Uses an even/odd version counter (`bloomFilterUpdateVersion`) to prevent caching
     GET results that overlap with a bloom filter update — avoiding a race where a key
     is cached locally but missing from the updated bloom filter.

2. **Server-side bloom filter state** (`CacheRequestProcessor`):
   - Stores one `BloomFilter<byte[]>` per listener per cache in a `ConcurrentMap`.
   - On every GET served, adds the key to the bloom filter (`addToFilter(key)`) so that
     future events for that key will pass the filter — this is the critical step that
     keeps the server-side filter in sync with the client's near cache.
   - On `UPDATE_BLOOM_FILTER_REQUEST`, replaces the bit set entirely
     (`filter.setBits(intSet)`).

3. **Event filtering** (`BloomAwareStatelessClientEventSender`):
   - Before sending a cache event to the client, checks
     `bloomFilter.possiblyPresent(event.getKey())`.
   - If `false` → skip the event (the client definitely doesn't have this key cached).
   - If `true` → send the event (the client might have it — possible false positive).
   - Bloom filter listeners are hardcoded to interest `0x0E` (created + modified +
     removed + expired) and cannot use custom filter/converter factories.

### What can be reused

| Component                         | Location                                                             | Hot Rod coupling                                                               | Reusable?                    |
|-----------------------------------|----------------------------------------------------------------------|--------------------------------------------------------------------------------|------------------------------|
| `BloomFilter<E>` interface        | `commons/all`                                                        | None                                                                           | Yes — as-is                  |
| `MurmurHash3BloomFilter`          | `commons/all`                                                        | None                                                                           | Yes — as-is                  |
| Bloom filter storage per listener | `server/hotrod` `CacheRequestProcessor.bloomFilters`                 | Map keyed by cache name, stores `BloomFilter<byte[]>` — no protocol dependency | **Extract to `server-core`** |
| Add-key-on-GET logic              | `server/hotrod` `CacheRequestProcessor.addToFilter()`                | 3 lines: look up filter, call `addToFilter(key)` — no protocol dependency      | **Extract to `server-core`** |
| Event filtering check             | `server/hotrod` `BloomAwareStatelessClientEventSender.isSendEvent()` | Single `possiblyPresent()` call — no protocol dependency in the check itself   | **Extract to `server-core`** |
| Bloom filter update (setBits)     | `server/hotrod` `CacheRequestProcessor.updateBloomFilter()`          | Deserialise `IntSet` from bytes, call `setBits()` — trivially portable         | **Extract to `server-core`** |
| Event serialisation + queuing     | `server/hotrod` `BaseClientEventSender`                              | Deeply coupled: `VersionedEncoder`, `Events.*`, Netty `Channel`, `listenerId`  | No — protocol-specific       |
| Client near cache logic           | `client/hotrod-client`                                               | `NearCacheService`, `InvalidatedNearRemoteCache`                               | No — client-specific         |

### Proposed refactoring: `BloomFilterManager` in `server-core`

Extract the protocol-independent bloom filter management into a new class in
`server-core` that both Hot Rod and gRPC can use:

```java
package org.infinispan.server.core.cache;

/**
 * Manages per-listener bloom filters for near-cache invalidation.
 * Protocol-agnostic — Hot Rod and gRPC wire their own event dispatch
 * around this shared state.
 */
public class NearCacheBloomFilterManager {

    // One bloom filter per listener registration.
    // Key: a listener identifier (opaque to this class).
    private final ConcurrentMap<Object, BloomFilter<byte[]>> filters =
        new ConcurrentHashMap<>();

    /**
     * Creates a new bloom filter for a listener registration.
     * Called when the client opens a near-cache listener.
     *
     * @param listenerId opaque identifier (byte[] for Hot Rod, stream ID for gRPC)
     * @param bloomBits  number of bits in the bloom filter
     * @return the created BloomFilter
     */
    public BloomFilter<byte[]> create(Object listenerId, int bloomBits) {
        BloomFilter<byte[]> filter =
            MurmurHash3BloomFilter.createConcurrentFilter(bloomBits);
        filters.put(listenerId, filter);
        return filter;
    }

    /**
     * Adds a key to the bloom filter for the given listener.
     * Called on every GET served so the server-side filter tracks what
     * the client's near cache contains.
     */
    public void addToFilter(Object listenerId, byte[] key) {
        BloomFilter<byte[]> filter = filters.get(listenerId);
        if (filter != null) {
            filter.addToFilter(key);
        }
    }

    /**
     * Replaces the bloom filter bits entirely.
     * Called when the client sends an updated bloom filter after
     * accumulating too many false positives.
     */
    public void updateBits(Object listenerId, IntSet bits) {
        BloomFilter<byte[]> filter = filters.get(listenerId);
        if (filter != null) {
            filter.setBits(bits);
        }
    }

    /**
     * Tests whether a key might be present in the client's near cache.
     * Called before dispatching an invalidation event.
     *
     * @return true if the event should be sent (key possibly present),
     *         false if definitely not present (skip the event).
     */
    public boolean possiblyPresent(Object listenerId, byte[] key) {
        BloomFilter<byte[]> filter = filters.get(listenerId);
        return filter == null || filter.possiblyPresent(key);
    }

    /**
     * Removes the bloom filter for a listener.
     * Called when the listener is closed.
     */
    public void remove(Object listenerId) {
        filters.remove(listenerId);
    }
}
```

### gRPC integration

The gRPC near-cache listener extends the `CacheListenRequest` with bloom filter
parameters and adds an `UpdateBloomFilter` RPC for mid-stream updates:

```protobuf
// ---------- Near-cache listener ----------

message CacheListenRequest {
  string cache_name = 1;
  int32 listener_interests = 2;
  bool include_current_state = 3;
  repeated bytes key_filter = 4;
  string filter_factory = 5;
  repeated bytes filter_params = 6;
  string converter_factory = 7;
  repeated bytes converter_params = 8;

  // Near-cache bloom filter support.
  // When > 0, enables bloom-filter-based event filtering.
  // The server creates a bloom filter with this many bits and only
  // sends events for keys that pass the filter.
  int32 bloom_filter_bits = 9;
}

// Sent by the client to replace the server-side bloom filter bits.
// The server identifies the listener by the cache name + stream context.
message UpdateBloomFilterRequest {
  string cache_name = 1;
  // Serialised IntSet — the complete set of bits in the bloom filter.
  bytes bloom_bits = 2;
}

message UpdateBloomFilterResponse {
  // Empty — acknowledgement only.
}

service CacheListenerService {
  rpc Listen(CacheListenRequest) returns (stream CacheEvent);

  // Updates the bloom filter for an active near-cache listener.
  rpc UpdateBloomFilter(UpdateBloomFilterRequest) returns (UpdateBloomFilterResponse);
}
```

### Alternative: bidirectional streaming

Instead of a separate `UpdateBloomFilter` unary RPC, the `Listen` call could use
**bidirectional streaming** where the client sends bloom filter updates on the request
stream:

```protobuf
message CacheListenMessage {
  oneof payload {
    CacheListenRequest subscribe = 1;
    bytes bloom_filter_update = 2;
  }
}

service CacheListenerService {
  rpc Listen(stream CacheListenMessage) returns (stream CacheEvent);
}
```

This keeps the bloom filter update on the same stream as the listener, making the
association implicit (no need to match by cache name). However, it changes the `Listen`
RPC from server-streaming to bidirectional, which adds complexity to clients that don't
use near-caching. **Recommendation: use bidirectional streaming** — the added complexity is
minimal (clients that don't use bloom filters simply send one message and never write
again), and it avoids the need to correlate a separate `UpdateBloomFilter` RPC with the
correct listener stream.

### Server-side flow (gRPC)

1. Client opens `Listen` bidi stream, sends `CacheListenRequest` with `bloom_filter_bits > 0`
2. Server calls `bloomFilterManager.create(streamId, bloomBits)` to create the filter
3. Server registers a `@Listener(clustered = true)` on the cache
4. On each cache event, server calls `bloomFilterManager.possiblyPresent(streamId, key)`:
   - `false` → skip, do not send `CacheEvent` on the stream
   - `true` → send `CacheEvent` to the client
5. When the gRPC handler serves a `CacheGet` for a key on a cache that has active bloom
   filter listeners, it calls `bloomFilterManager.addToFilter(streamId, key)` — this is
   the critical sync step that keeps the server-side filter aligned with the client's
   near cache
6. Client sends `bloom_filter_update` message on the stream when false positives exceed
   threshold → server calls `bloomFilterManager.updateBits(streamId, bits)`
7. On stream cancellation or connection close, server calls
   `bloomFilterManager.remove(streamId)` and removes the cache listener

### GET-to-bloom-filter sync across protocols

Step 5 above has a subtlety: the `addToFilter` call must happen regardless of which
protocol the GET arrived on. If a gRPC client has a near-cache listener but performs
a GET via REST or Hot Rod (unlikely but possible in mixed deployments), the bloom filter
must still be updated.

The cleanest approach is to make `addToFilter` a **cache-level interceptor** rather than
a protocol-level handler. This could be implemented as a cache interceptor in
`server-core` that checks for active bloom filter listeners on every GET and updates
them. However, the performance cost of checking on every GET (even when no bloom filter
listeners exist) argues against this. The pragmatic approach is:

- Each protocol handler calls `bloomFilterManager.addToFilter()` on GET
- Cross-protocol sync is a known limitation documented for users of mixed-protocol
  deployments — if a client uses gRPC for near-cache listening, it should also use gRPC
  for GETs on that cache

### Differences from Hot Rod bloom filter protocol

| Aspect                  | Hot Rod                                                        | gRPC                                                            |
|-------------------------|----------------------------------------------------------------|-----------------------------------------------------------------|
| **Registration**        | Separate opcode `ADD_BLOOM_FILTER_NEAR_CACHE_LISTENER_REQUEST` | `bloom_filter_bits` field in `CacheListenRequest`               |
| **Bloom filter update** | Separate opcode `UPDATE_BLOOM_FILTER_REQUEST`                  | `bloom_filter_update` message on the same bidi stream           |
| **Listener identity**   | `byte[] listenerId`                                            | HTTP/2 stream ID                                                |
| **Filter storage**      | `CacheRequestProcessor.bloomFilters` (Hot Rod module)          | `NearCacheBloomFilterManager` (server-core, shared)             |
| **Add-on-GET**          | `CacheRequestProcessor.addToFilter()`                          | gRPC handler calls `NearCacheBloomFilterManager.addToFilter()`  |
| **Concurrent safety**   | `IntSets.concurrentSet()`                                      | Same — reuses `MurmurHash3BloomFilter.createConcurrentFilter()` |
